# 写真協力（一般参加者からの写真の提供）：受付と承認の運用案

2026年11月13日。**まだ実装していない**（画面も受信側も未着手）。受信側と承認の仕組みができるまで、一般公開しない。

## 1. 今の仕組み（コードを追って確認したこと）

| 場所 | 今の動き |
| --- | --- |
| `site/assets/js/views/collect.js`（スタッフ用の画面） | `?staff=1` で開いた端末だけで使える。撮るときに**スタッフが番号（1〜36・other）を選ぶ**。写真は端末の中に保存し、合鍵（スタッフ用QRの `key=`）があれば「送付」、なければ ZIP 書き出し |
| `tools/collect_server/Code.gs`（Google Apps Script・受信側） | 合鍵（STAFF_KEY）が合えば受け取り、Google ドライブの `番号/個体/` のフォルダに保存。説明欄に label・group・時刻・メモ。**状態（未確認・採用可など）の欄はない** |
| `tools/fetch_collected.py`／`tools/import_collected.py` | ドライブ（または ZIP）の写真を、**番号のフォルダのまま** `training/photos/NN/個体/` に取り込み、`make_training_manifest.py` で一覧を作る |
| `tools/train.html`／`train.js` | 一覧の写真で学習し、評価してから、人がボタンを押して `site/models/classifier.json` を保存。**自動の再学習・自動の本番反映はない** |

分かったこと：
- 今は「撮った人が選んだ番号」がそのまま正解として学習に入る。スタッフ（貝に詳しい人）が撮る前提なので成り立っている。
- 受信側に「未確認」と「採用可」の区別がない。**このまま一般に開くと、参加者の自己申告が正解として学習に入ってしまう。**
- 公開しているコードにスタッフの合鍵は入っていない（QRコードのURLから端末に覚えさせる方式）。送付先のURLは公開の設定ファイルにあるが、合鍵なしでは受け取らない。
- `?staff=1` は画面の切り替えであって、認証ではない（合鍵が認証）。

## 2. 一般向けの流れ（案）

名称：「写真で調査に協力」（入口は「このサイトについて」と、判定結果の画面の控えめなリンク。ホームの主要カードにはしない）

1. 写真を撮る／選ぶ（表・裏・横、1枚に1個体、明るい場所・ピント、人や個人情報を写さない、の短い案内）
2. 写真を確認（同じ貝の複数枚は1つの組にまとめる）
3. 名前は任意（36種類から選ぶ／わからない／36種類にない）
4. 送る内容と使い道の確認（利用目的・送付先の運営・保存と削除・問い合わせ先）
5. 利用者が「送信」を押したときだけ送る。圏外なら「端末に保存・未送信」と表示し、あとで送れる

送る情報（別々の欄で持つ）：
- 写真（位置情報などの EXIF を消したもの）
- 投稿者が選んだ名前（任意。**自己申告**）
- AI の候補（上位と確からしさ。**候補**）
- 組の番号・撮影の向き・送信の番号（再送で二重に登録しないため）・時刻
- 運営が決めた名前（**運営だけが書く**。最初は空）

## 3. 正解データを守る仕組み（受信側・書き出し側・学習側で守る）

| 段階 | 必要な変更 |
| --- | --- |
| 受信（Apps Script） | 一般用の受付を、スタッフ用と**別の入口**にする。保存先は `投稿（未確認）/` の下だけ。番号のフォルダ（学習用）には書かせない。大きさ・枚数・形式の上限、同じ送信番号は1回だけ受け付ける。状態は必ず「未確認」から |
| 確認（運営） | ドライブの表（スプレッドシート）で、状態（未確認／採用可／保留／不採用）・運営が決めた名前・確認した人・日付・根拠を記録。詳しい人でも判別できないものは「保留」。必要なら博物館・専門家へ |
| 書き出し（fetch） | `fetch_collected.py` は「採用可」で、運営が決めた名前が入っている写真だけを取り込む。投稿者の名前・AIの候補は**学習のラベルに使わない** |
| 学習（train） | 今までどおり、人が実行して評価し、前より悪ければ入れ替えない。同じ貝・連写・ほぼ同じ写真は、学習用と評価用に分けない（個体単位で分ける）。入れ替えの前後を、同じ評価用の写真で比べる。種類別の間違い・36種類以外への反応も見る。前のモデルに戻せるよう、入れ替え前の `classifier.json` を残す |
| 権限 | 承認できるのは、ドライブを編集できる運営の人だけ（Google の権限）。公開のコードにスタッフ用の鍵を入れない |

静的な公開サイト（GitHub Pages）だけでは、受付・承認・権限の管理はできない。上の Apps Script の変更と、ドライブでの運営の作業が必要。

## 4. 画面の説明を、実装に合わせる

- 通常の「写真で調べる」は、今までどおり端末の中だけで処理（送信しない）。
- 写真協力を公開するときに、「このサイトについて」を次のように直す：
  「写真で調べるために選んだ写真は、端末内で処理します。『写真で調査に協力』で送信した写真は、運営へ送られます。」
- 投稿数が増えれば必ず精度が上がる、とは書かない。
