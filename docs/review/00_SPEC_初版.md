# 三十六歌仙貝 デジタルガイド 実装指示書

更新日：2026年9月29日

## Claude Codeへの依頼

増穂浦の「MASUHOGAURA 36 shells Collection」を、スマートフォン向けWebサイトとして実装してください。私はClaude Codeを使って自作します。このファイルと参照画像を読み、作業環境で起動して操作できるところまでコードを書いてください。

まず既存のプロジェクト構成と指示ファイルを確認してください。既存の構成があれば活用し、空のプロジェクトなら保守しやすく、無料で公開できる構成を選んでください。細かな実装判断は目的と参照画像に沿って進め、不可欠な情報が不足する場合にだけ具体的に質問してください。

## 1 企画の目的と対象

参加者は500円で水色の実物コレクションBOXを受け取り、増穂浦海岸で貝を拾って1番から36番まで埋めます。一度で集め切ることは基本的にできず、次回来訪時には貝が入った同じ箱を持参します。

サイトは実物の箱と海岸での貝探しを助ける道具です。主な役割は「探す」「見分ける」「箱の空きを確認する」。スマホの操作は短くし、現地で貝を探す時間を大切にしてください。

主な利用者は20〜30代の女性とその子どもです。柔らかくかわいい印象と、大人にも使いやすい読みやすさを両立してください。

## 2 参照画像とデザイン

参照画像はプロジェクトの `references/` フォルダに置く想定です。

| 資料 | 用途 |
| --- | --- |
| 承認済みのスマホ画面イメージ | 画面構成と見た目の最優先資料。提供されている場合は、ほぼその画像どおりに再現する |
| IMG_3525.jpeg | 既存チラシ。ロゴ、配色、線画、企画の世界観を確認する |
| IMG_0429.jpeg | 36種類の番号、名称、並びの確認資料 |
| IMG_4027.jpeg | 貝の実物写真の参考。番号との対応はこの写真だけから推定しない |

承認済み画面イメージが未配置の場合、その画像を確認したとは扱わず、チラシと本指示書を基準に実装してください。チラシの料金以外の受付場所や景品等の運用情報は、現行情報が確認されるまで自動的に転載しないでください。

### デザイン方針

- 淡い水色、ミルキーピンク、クリームイエロー、白、濃紺を基本にする。
- 既存の「36 shells Collection」のロゴと貝のイラストを活用し、チラシから自然につながる印象にする。
- 柔らかい角丸、余白、大きな操作領域、短い日本語を使う。
- 背景や装飾は淡くしても、本文と番号は屋外で読める濃さを確保する。
- スマートフォンの縦画面を優先し、片手でも操作しやすくする。
- 一般的な絵文字の多用を避け、既存の線画に合うアイコンを使う。
- 新しいロゴへの置き換え、過度なゲーム演出、機械的な解析演出は不要。
- 参照画像をページ全面に貼るだけで済ませず、実際に操作できる画面として再現する。

## 3 無料運用に関する必須条件

制作後も無料で運用できる構成を優先してください。Claude Code自体の利用料はサイトの運用費とは別です。

- 有料API、有料データベース、有料認証サービスを導入しない。
- 無料枠を使う場合は、採用時点の利用条件、容量、通信量、商用・自治体利用の可否、超過時の挙動を公式情報で確認する。
- 無料枠の超過で自動課金される構成にしない。
- 図鑑、検索、デジタル箱、端末内保存はブラウザ内で動作させる。
- 箱の読み取りと貝の判定は、ブラウザ内の画像処理・モデルによる実装を優先する。
- 無料で必要な精度を得られない場合は、限界と代替操作を示す。有料サービスに勝手に切り替えない。
- 3D表示の実装と、実物の3D素材の制作・入手は分けて扱う。
- 無料公開先の候補と制限をREADMEに記載する。公開が必要な段階では公開内容と方法を提示する。

## 4 全体の利用フロー

### 初めて使う

実物の箱を受け取る → QRからサイトを開く → 36種類から探す、または拾った貝を調べる → 実物を箱に入れる → 必要なときに箱を撮って空きを確認する。

### 次に来たとき

同じ実物の箱を持参する → サイトを開く → 端末内に残っていれば前回の目安を見る → 必要に応じて箱を撮り直す → 空いている番号から次の貝を探す。

ログイン、会員登録、メールアドレス、暗証番号、BOX IDは不要です。デジタル記録は目安であり、実物の箱を基準にします。ポイント、ランキング、デジタル景品、デジタル認定証は実装しません。

## 5 画面と機能

### 5.1 ホーム

ロゴと短い案内の下に、主な操作を3つ置きます。

- 「この貝、なあに？」：拾った貝を撮って調べる。
- 「貝を探す」：36種類の一覧を見る。
- 「箱を読み取る」：実物の箱の埋まり具合を見る。

端末内に記録がある場合は「箱を見る」から前回のデジタル箱にも進めるようにします。初回に長い説明や登録を要求しないでください。

### 5.2 36種類の一覧

- チラシにある番号・名称を基準に36種類を表示する。
- 写真、番号、名前をカードに表示する。
- 番号・名前で直接探せるようにする。
- 確認済みの属性がある場合は、色や形による簡単な絞り込みも設ける。
- カードから貝の詳細へ進む。
- デジタル箱の記録がある場合は、未収集の候補だけを見ることもできるようにする。

### 5.3 貝の詳細

番号、名称、確認済みの写真、見分けるポイント、似ている貝への導線を表示します。生態や由来などの長い説明より、現地で見るべき特徴を優先してください。

写真は可能なら表・裏・横を切り替えられるようにします。「3Dで見る」「ARで実物大を見る」を素材・対応状況に応じて用意します。似ている2種類は写真と確認済みの特徴を並べて比較できるようにしてください。

学名、サイズ、特徴、類似種の関係は創作しないでください。資料不足の情報は未確認としてデータ側で管理し、利用者向け画面に架空の説明を出さないでください。

### 5.4 拾った貝の撮影と判定

スマホのカメラ撮影と既存写真の選択に対応します。1枚の貝が見やすく写るよう、短い撮影案内を出してください。定規の持参や計測入力は要求しません。

解析が利用可能な場合は、次の結果を扱います。

- 有力な候補がある。
- 似た候補が複数あり、比較が必要。
- 36種類以外の可能性がある。
- 写真が不鮮明、または情報不足で判別できない。

結果には候補、確認する特徴、図鑑・比較への導線を表示します。「可能性が高そう」「似ている候補」「判別が難しい」のような自然な文言を使い、検証されていない確率の数字を出さないでください。必要なら裏側の写真を追加できるようにします。

無料モデルを使用する場合も、36種類への対応と実際の写真での精度を検証してください。汎用モデルを入れただけで正確に判定できるとは扱わないでください。

判定が未実装・利用不能の場合は、その状態を明示し、図鑑や色・形による絞り込みから自分で確認できるようにしてください。固定の貝名やランダムな結果を本当の判定として表示してはいけません。

### 5.5 デジタルの箱

実物の水色の箱と同じ4行×9列、36マスを表現します。番号と位置は参照資料で照合し、実物と一致させてください。スマホに合わせて番号の並びを勝手に組み替えないでください。

横長の箱をスマホで見せる際は、全体表示からマスを拡大して選べるようにするなど、全体の位置関係とタップのしやすさを両立してください。小さすぎるマスに長い名称を詰め込まず、選択時に番号と名前を大きく表示します。

- 埋まったマス：箱の写真から切り出した画像などで状態を表示する。
- 空いたマス：番号を示し、該当する貝の詳細へ進めるようにする。
- 判断できないマス：利用者が確認すべき状態だと分かる表示にする。
- 収集数は「箱の記録 12 / 36」など目安として表示する。
- 記録の修正と、詳細を見る操作を混同しないようにする。

### 5.6 箱の読み取りと修正

実物の箱全体を撮影、または写真から選択し、各マスを「貝あり／空／要確認」で読み取ります。箱内の貝の種類そのものを判定する必要はありません。指定位置に入っているという前提で、番号に対応する収集の目安を作ります。

箱全体が写る撮影枠と、向きが分かる短い案内を表示してください。向き・箱の範囲が不明な写真を、誤った番号に自動反映しないでください。必要に応じて利用者が箱の範囲や向きを直せるようにします。

読み取り後は36マスの確認画面を出し、間違ったマスだけタップで修正して「この状態で保存」を押せるようにしてください。「撮り直す」も用意します。未確認マスを勝手に収集済みに加算しないでください。

ブラウザ内の画像処理で安定しない場合も、手動でマスを選択して使える状態にしてください。撮影された貝の画像と、標本画像は区別して扱います。

### 5.7 保存と再開

同じ端末・ブラウザに箱の状態を保存し、次回も表示します。保存日時を記録し、新しい読み取り結果は利用者が確認してから更新してください。解析失敗で以前の記録を消さないでください。

ブラウザのデータ削除や別端末では記録が残らない場合があります。その場合も、実物の箱を撮れば再開できる設計にします。保存機能が使えない環境では簡潔な案内を表示し、その場での利用を続けられるようにします。

### 5.8 3D表示

実物に基づくモデルがある種類では、指で回転・拡大し、裏側まで確認できるようにします。可能なら表・裏・横へ戻す操作を設けます。重い素材は必要になったときに読み込んでください。

モデル未提供の種類を架空の形で代用して、本物の標本のように表示しないでください。素材がない場合は写真で確認できる導線を維持し、モデルを追加すれば拡張できるデータ構造にしてください。

### 5.9 AR表示

対応端末と実寸を確認したモデルがある場合に、実物大を目安として表示します。サイズは標本の寸法に基づき、個体差があることが分かる短い表現にしてください。AR表示の位置・縮尺精度や手のひらへの配置を、未検証のまま保証しないでください。

必要に応じて拡大表示と実物大への復帰を用意します。AR非対応時や起動失敗時は3D表示または写真へ案内し、行き止まりにしないでください。

## 6 データと素材の管理

36種類のマスターデータは画面に直接埋め込まず、まとめて修正できるファイル等で管理してください。少なくとも以下を保持します。

- 番号、表示名、箱内の行・列。
- 表・裏・横などの写真と出典。
- 確認済みの色・形・見分け方、類似候補。
- 3Dモデルの参照先、単位、確認済み標本寸法。
- 情報と素材の確認状態。

箱の記録はマスターデータと分け、各マスの状態、必要な写真、最終更新日時を保持します。画像の容量を抑え、端末内保存の失敗を扱えるようにしてください。

参照画像から読み取れない番号・名称や、写真との対応を推測で確定しないでください。未確認項目は `CONTENT_TODO.md` 等に一覧化します。素材の利用条件も記録してください。

## 7 共通の使いやすさとエラー処理

- 日本語表示とスマートフォンの縦画面を優先する。
- ボタンと操作領域を十分に大きくする。
- 色だけで状態を伝えず、文字や記号も併用する。
- 読み込み中、通信失敗、カメラ拒否、対応外の画像、容量超過を扱う。
- カメラを使えなくても写真の選択や手動操作に進めるようにする。
- 写真を外部へ送信する必要が生じる構成は、無料条件と写真の扱いを確認してから提案する。既定は端末内処理とする。
- 外部サービスの鍵を使うことになっても、秘密鍵をブラウザや公開コードに埋め込まない。
- 不要な個人情報や位置情報を収集しない。
- 主な画面には戻る導線を用意し、入力中や確認中の状態を不用意に失わせない。

## 8 実装の進め方

1. 既存環境と参照画像を確認し、簡潔な実装計画を示す。
2. ホーム、一覧、詳細、デジタル箱、撮影・確認の画面と遷移を実装する。
3. 手動でのマス修正、端末内保存、再開を完成させる。
4. 無料で実現できる箱の読み取りと貝の判定を検証し、利用可能な範囲を接続する。
5. 実物モデルがある種類に3D・ARを接続し、未提供素材の追加方法を整える。
6. 実際に起動して主要な操作を確認し、見た目を参照画像と照合して修正する。
7. README、必要な素材一覧、動作確認結果をまとめる。

専用素材が不足していても、独立して実装できる画面や保存処理は進めてください。見た目だけ完成した無反応なボタンを放置せず、利用可能な機能と準備中の機能が分かる状態にします。

## 9 完了時の確認項目

- ホームから3つの主な操作へ迷わず進める。
- 一覧、詳細、箱の番号対応が参照資料と一致している。
- 小さいスマホ画面でも文字や操作が破綻しない。
- 箱の状態を修正・保存し、再読み込み後も再現できる。
- 新しい読み取り結果は確認してから反映され、失敗時に以前の状態が消えない。
- 判定不能や36種類以外を扱い、架空の判定結果を表示しない。
- 画像認識の精度は、実際に検証した範囲だけを報告する。
- 3D素材がない場合とAR非対応時にも、写真から確認できる。
- 無料運用の条件と制限が明示され、有料サービスが勝手に導入されていない。
